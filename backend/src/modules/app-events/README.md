# Модуль SSE-событий (AppEvents)

## Назначение

Единая шина уведомлений фронтенду: модуль держит поток Server-Sent Events, в
который остальные модули кладут события об изменениях. Фронтенд подписывается
один раз и по типу события решает, что перезагрузить — список книг, строки
ведомости, свои роли.

## Файловая структура

```
app-events/
├── README.md                этот файл
├── app-events.controller.ts SSE-маршрут
├── app-events.module.ts     модуль NestJS
└── app-events.service.ts    поток событий и методы-уведомители
```

Ни DTO, ни сущностей, ни guard'а в модуле нет.

## Маршруты

Префикс — `/api`.

| Метод | Путь | Что делает | Авторизация |
|---|---|---|---|
| `GET` | `/api/app-events/sse` | поток SSE; фронт подключается через `EventSource` | нет |

Формат на проводе — `event: message` и `data: <JSON>`. Контроллер оборачивает
событие в `MessageEvent('message', ...)`, поэтому имя SSE-события всегда
`message`, а настоящий тип (`objects-changed`, `access-changed`, …) лежит внутри
JSON, в поле `data.type`.

## Ключевые методы сервиса

| Метод | Зачем | Кто вызывает |
|---|---|---|
| `notifyAccessChanged(userId)` | изменились права доступа | в бэкенде вызовов нет |
| `notifyUserDataUpdated(userId)` | изменились данные пользователя (аббревиатура) | в бэкенде вызовов нет |
| `notifyMolAccessChanged(userId)` | изменился доступ МОЛа к инвентаризации | `MolAccessService` |
| `notifyInventoryStatementLoaded(email)` | пришли новые инвентаризационные ведомости | `InventoryStatementParser` |
| `notifyInventoryBookChanged(bookId)` | книга изменена (создание, правка, удаление) | `InventoryBooksService` |
| `notifyObjectsChanged(userId, zavod, sklad)` | изменились объекты на складе | `ObjectsController` |
| `getEventStream()` | `Observable` для SSE-контроллера | `AppEventsController` |
| `emit(event)` (private) | пишет событие в лог и кладёт его в `Subject` | внутри сервиса |

Тип события — локальный интерфейс `AppEvent`: `{ type, message, data? }`.

## Особенности

- **Поток — обычный `Subject`, а не `ReplaySubject`:** событие получают только
  те, кто уже подписан; истории и буферизации нет.
- **Состояние живёт в памяти процесса.** Второй экземпляр бэкенда не увидит
  чужих событий, перезапуск процесса рвёт все подписки (переподключение — на
  стороне фронтенда, до пяти попыток).
- **События не адресные:** поток общий для всех клиентов, `userId` внутри данных
  нужен лишь для того, чтобы каждый клиент мог отличить свои изменения от чужих.
- **Маршрут без авторизации**, хотя данных в событиях хватает (email, id
  пользователя, завод и склад). Фронтенд подключается `EventSource`, который не
  умеет передавать заголовок `Authorization`; в коде причин не описано.
- **Два уведомителя в бэкенде никто не вызывает** (`notifyAccessChanged`,
  `notifyUserDataUpdated`) — фронтенд их слушает и обрабатывает.
- **Логирование:** `emit` пишет каждое событие в лог приложения через `Logger`
  с пометкой `[SSE]`; все `notify*`-методы идут через него, так что лог один.
- **Связи:** модуль не импортирует ничего и не зависит от базы; экспортирует
  `AppEventsService`, его импортируют `ObjectsModule` и `InventoryModule`.
