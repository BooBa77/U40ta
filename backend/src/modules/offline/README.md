# Модуль офлайн-режима (Offline)

## Назначение

Приложение — PWA, и работа на складе идёт без устойчивой связи. Модуль отдаёт
клиенту **весь срез данных одним запросом** для локального кэша (IndexedDB),
принимает накопленные в офлайне изменения и применяет их к базе, разбирая, что
пользователь вправе сделать сам, а что уходит на модерацию.

## Файловая структура

| Файл | Назначение |
|---|---|
| `offline.controller.ts` | HTTP-маршруты |
| `offline.module.ts` | Модуль NestJS; подключает почти все доменные модули |
| `services/offline.service.ts` | Точка входа: отдать данные, принять изменения, решить, нужна ли выгрузка |
| `services/offline-cache.service.ts` | Сборка среза данных из всех таблиц |
| `services/offline-sync.service.ts` | Применение изменений, пришедших из офлайна |
| `dto/offline-data.response.dto.ts` | Форма ответа со срезом данных |
| `dto/sync-changes.request.dto.ts` | Форма запроса на синхронизацию (см. «Особенности») |
| `dto/sync-object.dto.ts`, `dto/sync-inventory-book-item.dto.ts` | Изменения по объекту и по строке инвентарной книги |

## Маршруты

Весь контроллер закрыт `JwtAuthGuard`.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/offline/data` | срез данных для кэша: объекты, ведомости, QR-коды, фото, предложения, инвентарные книги и их строки, игнор-слова + сводка `meta` |
| `POST` | `/api/offline/check-switch-to-online` | есть ли что выгружать; если нечего — клиент чистит кэш |
| `POST` | `/api/offline/sync` | применить накопленные изменения |
| `GET` | `/api/offline/status` | заглушка: отдаёт `userId` и время, состояния синхронизации не считает |

## Ключевые методы сервиса

| Метод | Зачем |
|---|---|
| `OfflineService.getOfflineData(userId)` | срез данных через `OfflineCacheService.getAllData` |
| `OfflineService.checkIfSyncNeeded(localChanges)` | решает, нужна ли выгрузка; метод **синхронный** |
| `OfflineService.syncChanges(userId, dto)` | делегирует в `OfflineSyncService.applyChanges` |
| `OfflineSyncService.applyChanges(...)` | применяет изменения объектов, строк инвентарных книг и предложений |
| `OfflineSyncService.transformToProposedChanges(...)` | изменения «не-МОЛ» превращает в предложения для модерации |
| `OfflineSyncService.saveObjectLogs(...)` | сохраняет историю объекта, накопленную в офлайне |

## Особенности

Главное, что здесь надо знать, — и что стоит поправить:

- **Валидация синхронизации отключена.** В контроллере закомментированы и
  `@UsePipes(new ValidationPipe(...))`, и типизированное тело
  (`@Body() body: SyncChangesRequestDto`): принимается `body: any`. DTO
  `SyncChangesRequestDto` существует, но не применяется.
- **Ошибки уходят с кодом `200`** и телом `{ success: false, … }`: исключения
  ловятся внутри `try`. В `/data` при ошибке возвращается пустой срез с
  `success: false` и текстом ошибки в `message`.
- **`/api/offline/status` ничего не проверяет** — только `userId` и время. Если
  он нужен мониторингу, его надо реализовать.
- **`confirmCacheClear()` не вызывается ниоткуда** — такого маршрута нет. Именно
  он пишет в таблицу `logs` с источником `offline_mode`, и последняя такая
  запись в боевой базе от 27.07.2026: механизм молчит.
- **Конфликты решаются по правам, а не по времени изменения.** Если у
  пользователя нет прав МОЛ на склад, изменение не применяется, а превращается в
  предложение (`proposed_changes`) для модерации; изменения МОЛ применяются сразу.
